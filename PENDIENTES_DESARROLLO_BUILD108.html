6. Seguridad
🛡
OWASP ZAP + Playwright Security Tests
Seguridad · Cabeceras HTTP · Ataques controlados
⬆ 1 Alta  ● 2 Media
Alta
Cabeceras HTTP de seguridad X-Frame-Options y X-Content-Type-Options ausentes
El frontend no envía dos cabeceras HTTP críticas de seguridad que los navegadores modernos utilizan para proteger al usuario:

• X-Frame-Options AUSENTE: Permite que la aplicación sea embebida en un <iframe> desde cualquier dominio externo, habilitando ataques de Clickjacking donde el atacante superpone la app sobre contenido malicioso.
• X-Content-Type-Options AUSENTE: Permite que navegadores antiguos realicen MIME sniffing, pudiendo interpretar y ejecutar contenido no esperado (por ejemplo, ejecutar un archivo CSV como JavaScript).
Evidencia: Security Report → Security Headers Tests → Missing clickjacking protection (X-Frame-Options or CSP frame-ancestors) y Missing X-Content-Type-Options header. Pruebas falladas en qa/ui/tests/security.spec.ts líneas 33 y 44.
🔧
Acción requerida — Corrección de 10 líneas en FRONTEND/next.config.js

Agregar el bloque headers() en la configuración de Next.js: 
async headers() {
  return [{
    source: '/(.*)',
    headers: [
      { key: 'X-Frame-Options', value: 'SAMEORIGIN' },
      { key: 'X-Content-Type-Options', value: 'nosniff' },
      { key: 'Referrer-Policy', value: 'strict-origin-when-cross-origin' },
    ]
  }]
}
Media
Cabecera Content-Security-Policy (CSP) ausente — Recomendada para producción
No existe una política de seguridad de contenido (CSP) configurada. Sin CSP, el navegador no tiene instrucciones sobre qué fuentes de scripts, estilos e iframes son legítimas, lo que facilita ataques XSS de segundo nivel y carga de recursos externos no autorizados.
Evidencia: Security Report → Security Headers → ⚠ Content-Security-Policy header is missing (recommended for production). Prueba pasó como warning (no bloqueante) en qa/ui/tests/security.spec.ts línea 48.
🔧
Acción recomendadaDefinir una CSP inicial permisiva y luego ir restrictiendo. Ejemplo base en FRONTEND/next.config.js: 
{ key: 'Content-Security-Policy',
  value: "default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; img-src 'self' data: https:;" }
Usar la herramienta CSP Evaluator de Google para validar la política antes de aplicarla en producción.
Media
No hay pruebas de autorización (IDOR) ni de JWT tampering
Las pruebas de seguridad actuales validan CSRF, XSS y SQLi, pero no cubren: (1) que un usuario autenticado no pueda acceder a datos de otro usuario (Insecure Direct Object Reference — IDOR), ni (2) que el backend rechace tokens JWT manipulados (expirados, con firma inválida o con payload modificado).
Evidencia: Security Report → tests pasados: CSRF ✓, XSS ✓, SQLi ✓. Tests no existentes: IDOR, JWT tampering. Archivo de tests: qa/ui/tests/security.spec.ts
🔧
Acción recomendada — Dos frentes:

Backend (Go): Agregar tests unitarios en los handlers que accedan a recursos por ID de usuario, verificando que el middleware de autenticación compara el user_id del token con el recurso solicitado.

QA (Playwright/Newman): Agregar en qa/ui/tests/security.spec.ts un test que intente acceder a /api/v1/users/OTRO_ID con el token de un usuario diferente y espere un 403 Forbidden.
