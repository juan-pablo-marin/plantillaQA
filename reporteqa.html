Resumen Ejecutivo

Este documento consolida las evidencias de aseguramiento de calidad y controles de seguridad implementados en el proyecto Ficha Caracterización. Se detallan las estrategias de pruebas funcionales y no funcionales, así como el análisis estático de código y controles de seguridad perimetral y de aplicación. Todas estas validaciones son orquestadas automáticamente mediante nuestra arquitectura de integración continua (CI/CD) con Docker y Jenkins.

QA Dimensión 1 — Calidad del Software

Estándares de Desarrollo y Revisión (Code Review)

Se han adoptado convenciones estrictas para mantener el código ordenado y unificado:

  • Estrategia de Versionamiento: Utilizamos una estructura controlada de ramas en Git. Tenemos una rama principal donde reside el código estable y ramas secundarias para desarrollar nuevas características sin afectar el sistema actual.
  • Code Review: Ningún código nuevo entra al sistema sin que otro programador del equipo lo revise y lo apruebe.

Pruebas Funcionales: Asegurando que el sistema hace lo que debe

El stack de pruebas funcionales garantiza que el sistema cumpla con todos los requerimientos y que ninguna funcionalidad esté rota para el usuario.

1. Pruebas End-to-End (E2E) con Playwright

Utilizamos Playwright para simular el comportamiento exacto de un usuario real utilizando el sistema a través de un navegador web, validando la interfaz gráfica.

💡 En palabras sencillas: Playwright es como un "robot" que configuramos para que entre a nuestra página web, haga clic en los botones, llene los formularios de registro de inicio a fin y pulse "Guardar". Su trabajo es asegurar que todo funcione tal y como lo haría una persona real frente a su pantalla, comprobando que no existan errores visuales o procesos atascados.

2. Pruebas de API con Newman

Mediante Newman (la versión automatizada de Postman), evaluamos directamente la capa de servicios (el backend o motor del sistema) comprobando que las reglas de negocio y los datos viajen correctamente.

💡 En palabras sencillas: Si el sistema fuera un restaurante, Newman sería un supervisor que llama constantemente desde la cocina directamente a los cocineros para verificar que estén entregando el menú correcto con los ingredientes correctos, sin tener que esperar a que el mesero (la pantalla del usuario) le lleve el plato.

Pruebas No Funcionales: Asegurando rendimiento y capacidad

Validamos la resiliencia del sistema bajo carga y medimos detalladamente los recursos técnicos consumidos.

1. Pruebas de Carga y Estrés con k6

Usamos k6 para generar tráfico masivo al sistema, simular múltiples conexiones simultáneas e identificar el límite en el cual la aplicación podría empezar a degradarse.

💡 En palabras sencillas: k6 nos permite simular un "Black Friday" digital. Enviamos docenas o cientos de visitantes virtuales al mismo tiempo a la plataforma para comprobar que no se sature, que no se caiga y que las respuestas sigan siendo rápidas, incluso cuando todos hacen clic a la vez.

2. Monitoreo y Telemetría con Grafana, Prometheus y cAdvisor

Para tener visibilidad completa durante las simulaciones de carga y la salud del sistema, utilizamos un conjunto de herramientas complementarias que extraen, almacenan y grafican datos vitales de nuestra infraestructura.

💡 En palabras sencillas: Si la plataforma fuera un vuelo comercial, cAdvisor y Prometheus serían los múltiples sensores externos adheridos a los motores y al fuselaje recopilando datos de temperatura y presión segundo a segundo. Por su parte, Grafana funciona como las pantallas del tablero de mandos en la cabina del piloto, traduciendo toda esa complejidad de sensores en gráficos visualmente amigables con agujas y alertas de colores para tomar decisiones rápidamente.

UX Dimensión 1.5 — Usabilidad del Software

Accesibilidad (WCAG 2.1 AA) con axe-core

Utilizamos axe-core integrado con Playwright para escanear cada pantalla de la aplicación de forma automática, verificando que cumpla con los estándares internacionales de accesibilidad web WCAG 2.1 nivel AA.

💡 En palabras sencillas: axe-core es como un inspector de accesibilidad universal que entra a cada pantalla de nuestra aplicación y revisa que personas con discapacidades visuales, motoras o cognitivas puedan usarla sin problemas. Verifica que los colores tengan suficiente contraste para ser leídos, que todos los botones y campos tengan etiquetas claras para lectores de pantalla, y que la navegación con el teclado funcione correctamente.

Core Web Vitals con Lighthouse

Integramos Google Lighthouse para medir automáticamente las métricas de experiencia de usuario que Google considera esenciales para una buena interacción: tiempos de carga, estabilidad visual y capacidad de respuesta.

💡 En palabras sencillas: Lighthouse es como el "velocímetro de calidad" que usa Google para evaluar las páginas web. Mide tres cosas fundamentales: (1) LCP — ¿cuánto tarda en aparecer el contenido principal en la pantalla?; (2) TBT — ¿la página responde rápido cuando el usuario intenta hacer clic?; y (3) CLS — ¿se mueven los botones o textos mientras carga la página, haciendo que el usuario haga clic en el lugar equivocado? Estas métricas determinan si la experiencia del usuario es fluida o frustrante.

SEC Dimensión 2 — Seguridad del Software

Controles de Acceso

Implementamos mecanismos robustos definidos por la experta de seguridad para la protección de la identidad:

  • Autenticación: Uso de JWT (JSON Web Tokens) para sesiones cifradas y seguras.
  • Autorización: Control de acceso basado en roles (las personas solo pueden ver la información a la cual tienen permisos asignados).

Desarrollo Seguro: Análisis Estático con SonarQube

Se ha integrado SonarQube, una herramienta de Análisis Estático de Seguridad de Aplicaciones (SAST), orientada a mitigar riesgos basados en el estándar OWASP Top 10 (prevención contra inyecciones SQL y ataques del tipo Cross-Site Scripting).

💡 En palabras sencillas: SonarQube actúa como un corrector ortográfico o un auditor hiper-avanzado que lee todo el código que escriben los programadores antes de que este se convierta en la aplicación final. En lugar de buscar comas mal puestas, el auditor busca "debilidades de seguridad" invisibles y "malas prácticas" previniendo que un cibercriminal aproveche esas fisuras en el futuro.
